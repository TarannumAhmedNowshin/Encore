# src/lib/encore rules

- AI usage is recorded only after a call returns a usable answer; why: failed calls must not consume the daily limit.
- Journey-rail stage statuses are computed by the pure `computeStages` in `src/lib/encore/deal.ts` from live counts (`stages-query.ts`); why: one tested rule set, no hard-coded statuses.
- Smart-tier pipeline AI calls fall back to the fast model on 503 (`generateJsonWithFallback`) and set `runs.used_fallback_model` so the page can say so; why: the main model is often overloaded.
- The People stage (`src/lib/encore/people.functions.ts`: findPeople, scoreContacts) maps LinkedIn candidates to personas/slots with the fast model; pure rules (titleKeywords, ROLE_SLOTS, isCreditError) live in `src/lib/encore/people.ts`; why: bulk runs go one company at a time on the free provider tiers, so rules must be testable without provider calls.
- Evidence quotes pass `isUsableEvidence` in `src/lib/encore/discover.ts` (length, contact details, contact pages, third-party mentions) in both qualify-company and find-departments; why: one tested rule set for what counts as evidence.
- Outreach (`src/lib/encore/outreach.functions.ts`: draftOutreach) grounds every claim in a numbered fact; pure rules in `src/lib/encore/outreach.ts`: expected_outcomes/success_criteria facts are prefixed "TARGET (not yet achieved):", business_impact/pain_point "BEFORE:"; a claim on a TARGET fact fails on past-tense achievement verbs (PAST_TENSE); factual sentences not covered by a verified claim are stored as unverified `ungrounded` claims (red underline); email/executive_intro/linkedin_message need a verified claim on a target-evidence fact when the target has any. Why: drafts must be verifiable in code, never auto-sent, and never present goals as results or invent relevance.
- Outreach review uses pure `outreach-review.ts` for effective body, status membership and edited-claim coverage; generation preserves approved channels. Why: approval/export must agree with the reviewed text and regeneration must not delete approvals.
- Usage limit checks and displays both use `dailyLimitFor` and rolling usage events; `nextUsageReset` reports the next expiring unit. Why: company-search usage and displayed allowances must agree.
- External run-store hooks keep a stable initial snapshot in a ref. Why: fresh array/object defaults on re-render violate useSyncExternalStore snapshot stability and interrupt interactions.
- Landing email selection is pure in hero.ts and uses the effective approved body with lossless story-text segments; the sanitised public demo alone is cached in sessionStorage with an expiry. Why: reviewed text and highlights must agree, and private analyses must never enter the public cache.
- Empty people searches retry once through peopleWithBroaderRetry; provider failures propagate, and Apify logs only terminal status/item count. Why: unavailable searches must never appear as genuine no-match gaps or expose identities/secrets in logs.
- Analysis settings (rename, region, anonymise, delete) live in `src/lib/encore/analysis.functions.ts`; deleteAnalysis removes storage files from the documents bucket and all child rows before the analysis row. Why: owner-only mutations with the standard owner check.
